# Security Model and Trust Contract

**Status date:** 2026-10-23

**Source snapshot:** branch `infothon/rapid-integration`, based on pushed commit `252673f64c4a0c7cf0c0fee076b6209cad419276`; the current working tree adds local OIDC role-based management authorization and one-time pending enrollment challenges.
**Design status:** the baseline includes the isolated feature-off Go verifier, Python v1 binding implementation, SQLite observation store/resolver, local identity/binding lifecycle primitives, read-only mTLS support, and an unverified-by-default policy registry. Current local changes validate configured OIDC bearer tokens against a bounded trusted JWKS fetch/cache and enforce management roles; they also create, inspect, revoke, and atomically consume persisted pending enrollment challenges. The working tree adds a SQLite hash-chained security event service, trust-pin-gated policy review, and a tested policy-aware read-only Ubuntu assessment flow. The latter compares Controller-owned reviewed policy controls with discovery and assessment results, but does not cryptographically attest the agent binary; loopback tunnel results remain unauthenticated. Ephemeral-key and disposable-database tests exercise these slices. No OIDC provider deployment, identity proof, certificate issuance, authenticated enrollment, production PKI, trusted policy authority, approval authorization, external immutable audit sink, or end-to-end execution is established. The system is not production-approved.

This document describes the security boundary required before remote privileged remediation. The local policy-aware assessment integration changes only the read-only assessment route; it does not authorize execution. Historical live verification remains limited to Ubuntu status, assessment, and plan through the lab tunnel. No live privileged execution or rollback has been performed.

## 1. Current implementation and trust boundaries

- **Target agent:** Go `net/http` agent. Default listener is `127.0.0.1:9000`. Local code adds an all-or-nothing mTLS listener configuration using `AGENT_TLS_CERT_FILE`, `AGENT_TLS_KEY_FILE`, `AGENT_TLS_CLIENT_CA_FILE`, and `AGENT_TLS_CONTROLLER_IDENTITY`; it requires a verified client certificate and exact configured Controller URI SAN. Without complete TLS settings, plaintext binding must remain loopback. The optional code has not been deployed to the VM.
- **Controller:** FastAPI application with SQLite persistence and SQLAlchemy models. Current local code validates OIDC JWTs against only the configured issuer, audience, role claim, and HTTPS JWKS endpoint, with explicit RS256/ES256 allowlisting, bounded token/JWKS sizes, a bounded key cache and three-second HTTPX phase timeouts, and fail-closed behavior if configuration or keys are unavailable. Target creation requires the configured admin role; target reads and read-only agent status/assessment/plan routes require the configured read role. Enrollment challenge management and policy review require separate configured roles. Health remains public; API documentation routes are disabled. There are no execute/rollback Controller routes or deployed OIDC identity provider. The new database hash chain detects local inconsistency but is not immutable or rewrite-resistant against a database administrator; there is no external/WORM audit service.
- **Enrollment challenge slice:** enrollment-admins can create a Controller-issued pending identity and target-scoped challenge in one database transaction. A random token is returned once with no-store headers; only its SHA-256 digest is persisted. Challenge metadata can be inspected/revoked; consumption is atomic and single-use. Creation, expiration, consumption and revocation append sanitized audit events in the same transaction (consumption is attributed as an unauthenticated system-observed token-possession event). This service does not prove agent identity or key possession, issue certificates, activate identity/credentials/bindings, or create approval-ready provenance. It is not authenticated agent enrollment.
- **OIDC management authorization slice:** the application accepts bearer access tokens only after signature, issuer, audience, time, key-type/algorithm, and configured role-claim checks against the configured trusted JWKS endpoint. Token-supplied key material/URLs and unsupported JOSE headers are rejected; duplicate JSON members in JWT and JWKS documents fail closed. Test-only ephemeral JWKS do not represent a deployed IdP or production identity assurance. The role claim's organizational meaning and role assignment policy remain operator-configured and require review.
- **Target record and local identity primitives:** `Target.id` remains Controller-owned. Local changes add AgentIdentity, AgentCredential and historical TargetAgentBinding records, with unique agent IDs, unique certificate and optional public-key fingerprints, lifecycle states, expiry/revocation metadata, and generation UUIDs. Local service functions replace/revoke/quarantine records and invalidate binding-dependent assignments. They are not HTTP endpoints, do not prove possession, and do not enroll an agent. Calling a lifecycle primitive or writing a database row is not authenticated identity.
- **Controller-to-agent client:** the current local client uses an explicit CA file, client certificate/key, and Controller workload URI for HTTPS; Python's standard verified SSLContext performs normal chain/hostname checks. It additionally matches the peer certificate's DER SHA-256 and URI SAN to the active Controller target-agent binding and active credential. It disables redirects and environment proxy inheritance. TLS failures and identity mismatches do not downgrade to HTTP. HTTPS without complete TLS settings is refused.
- **Read-only HTTP boundary:** URL resolution permits plaintext only on loopback. Explicit loopback HTTP remains available for the SSH-tunnel lab; non-loopback HTTP is rejected, including the default remote-address path. Partial mTLS configuration also rejects even loopback HTTP rather than silently downgrading. This change does not configure the VM or production trust roots.
- **Authenticated transport status:** the Go listener requires CA-verified mutual TLS and validates the Controller URI SAN; the Controller validates the agent chain and URL hostname, then checks the leaf fingerprint and URI against its active binding. It rechecks the active binding before consuming response bodies, and assessment persistence checks an in-process receipt from that verifier against the active binding/credential again. Persisted authenticated status means only that the response arrived over a channel bound to that Controller record at collection time. It does not authenticate assessment contents independently, authorize policy, or imply approval. These are local implementation/test behaviors, not a production deployment or enrollment guarantee. Certificate revocation is checked against Controller credential state after TLS response headers arrive; a production CRL/OCSP or short-lived credential distribution policy remains undecided.
- **Controller-owned policy/catalog registry and review:** local tables store platform, policy/catalog versions, canonical definition bytes, domain-separated SHA-256, source reference, verification/applicability states, enablement and target assignment generation. Definition contract v1 canonicalizes JSON as UTF-8 with sorted object keys, compact separators and no NaN, then hashes `policy-catalog-definition/v1\0 || canonical-json`. Registration always creates disabled, unverified, unconfirmed records. A separate policy-review role is required and is unconfigured by default. Approval additionally requires operator-provisioned `POLICY_REVIEW_TRUST_PINS_JSON` to match the exact definition digest, source-evidence digest/reference, platform, policy version, catalog version and explicit applicability flag. Review rows and enable/reject/revoke transitions are recorded and linked to audit events in the same transaction; a changed definition or latest non-approval invalidates the prior review. No trust pins or authoritative production policy definitions are provisioned by this change, so no policy is eligible for real approval. A pin is a trusted deployment configuration assertion, not independently verified evidence. This is not a comprehensive CIS catalog or formal compliance claim.
- **Lab tunnel:** The verified Ubuntu path used a local SSH forward to the agent's loopback listener. It supports only the documented lab read-only demonstration. It does not authenticate an application-level agent identity, bind a plan approval to a host, or establish production transport security.
- **Execution handlers:** Agent `/execute` and `/rollback` require POST and a bearer value matching `AGENT_EXECUTION_TOKEN`. An empty/unset variable returns 503 before executor invocation. The secret is shared and has no agent, user, target, or action scope. `/execute` also accepts `approved: true`; that client-controlled boolean is not proof of an authenticated human approval. Rollback currently has no request-body approval contract.
- **Executor:** One SSH root-login action has state capture, verification, automatic recovery, and rollback code with fake-operation unit tests. The executor has no Controller orchestration or approval-verifier integration, replay store, or tamper-evident audit integration. No live privileged action or rollback has been tested.
- **Isolated approval verifier and binding contracts:** `agent/internal/approval` verifies a compact signed envelope against explicit issuer/audience/agent/target/binding-generation/operation/action/policy context and an out-of-band trusted public-key map. It accepts ES256 only, checks the expected `kid` and token type, rejects untrusted key headers and unknown claims, requires `sub` to match the attested `approver_id`, and validates bounded time claims. In the current working tree it also accepts execute-only plan/evidence digest claims or a rollback-only recovery-manifest digest claim, comparing them to expected values supplied by the trusted caller. Deterministic binding APIs recompute those values from caller-supplied plan/evidence/recovery state. Go and Python independently check the shared exact-byte vectors. The package remains disconnected from handlers, Controller routes and executor; no production keys or credentials are loaded.
- **Controller binding module (this checkpoint):** `controller/app/approvals/bindings.py` provides typed Python canonicalizers and SHA-256 digests for the same action/evidence/plan/recovery v1 contracts and independently checks the Go vectors in tests. Plan/evidence binding takes target ID from Controller target context; recovery-manifest binding requires expected target context and rejects target mismatch, plus agent/generation mismatch when those expected values are present. The module rejects agent-supplied target/agent/digest fields in assessment payloads and bounds its UTF-8 JSON input. When authenticated context is required, labels/references alone fail; a future external provenance-verifier callback must explicitly validate the record. This module does not implement that verifier, authenticate observations, establish trustworthy provenance, persist records, or mark any digest dispatch-ready. Current `Target` storage lacks enrolled agent ID and binding generation, so authenticated-context validation cannot currently pass and recovery identity cannot yet be verified against enrolled agent/generation data. No handler, route, executor, or approval-dispatch integration uses this module.
- **Assessment observation and policy integration:** the assessment GET path now requires a resolved active target assignment and uses `aha-agent-assessment-policy/v1`, a bounded policy-definition shape containing platform, exact reported OS release, architecture, and an ordered list of control IDs/expected values. Resolution calls the existing registry verifier, which checks target-agent binding generation, active identity/credential, current reviewed definition digest, trust pin, enablement, and platform. The route reads `/discovery` and `/assessment`, matches reported OS/version/architecture and exact ordered findings to the assigned definition, then stores the raw validated response with Controller-derived policy/catalog versions and returns the policy version/catalog version/definition digest. Findings remain in the assessment object; planning recommendations remain on the distinct `/plan` endpoint. The raw discovery details and policy metadata are not treated as cryptographic agent attestations. The response exposes whether the mTLS agent channel was authenticated; the loopback SSH tunnel reports false and observations remain unauthenticated. The observation and sanitized success audit event are committed together; failed policy, transport, or result validation produces only a sanitized `assessment.failed` event, never an `assessment.collected` event. Storage/audit failure fails the request; audit failure rolls back successful observation storage. The digest is not tamper-evident audit and no approval context is returned.
- **Existing SQLite initialization:** app startup calls SQLAlchemy `Base.metadata.create_all`. This adds the identity, credential, binding, policy-registry and observation tables/triggers to an existing database. It does not alter existing `targets` columns. Temporary-database tests verify additive table creation; no column migration is needed for these additions. The user's existing database was not opened or modified during this change.
- **Verifier limits:** A valid signature proves only that a configured signing key signed those claims. It does not authenticate a human, prove the approver's role, or establish that the issuer recorded a valid approval. The verifier does not consume `jti`; replay remains possible until durable atomic replay storage is implemented and integrated. The verifier's expected digest configuration must be computed/derived by a trusted caller from authoritative objects; it does not load authoritative plan, assessment, policy, or recovery state itself. Its digest contracts do not establish immutable provenance, human approval, authorization, replay safety, or audit. Approval issuance, enrollment/key lifecycle, transport authentication, policy authorization, durable audit, handler integration and end-to-end execution remain absent.
- **Evidence limits:** Local recovery state is not a project audit trail. Handler unit tests establish only their tested request rejections and zero-call assertions; they do not prove end-to-end trust or production security.

### 3.9 Controller assessment observations and resolution

`AssessmentObservation` is a durable, target-attributed record of a validated agent response. The versioned representation `agent-assessment-json/v1` stores the exact original UTF-8 JSON text, collection timestamp, source, assessed platform, optional policy/catalog versions, optional self-reported agent ID, optional target binding generation, and `sha256:<hex>` over the exact response bytes. The HTTP reader enforces the parser's 4 MiB bound while streaming. The API preserves the existing assessment object and adds `assessment_observation_id` and `assessment_trust_status` so a client can reference the stored observation. Storage failure returns HTTP 503 rather than reporting an observation as persisted.

The insert service derives target ID/platform and current generation from Controller-owned records. Loopback HTTP receives unauthenticated status. For mTLS collection it accepts only an in-process receipt minted by the TLS verifier, then rechecks its seal, target, generation, active credential, fingerprint, URI and validity before recording channel-authenticated metadata. A digest or reported agent ID cannot upgrade the record. SQLite constraints and triggers prevent ordinary inserts with approval-trusted status and ordinary updates/deletes. These controls protect normal application use and expose corruption, but are not tamper-evident audit: a database-level actor can alter the payload, hash, or triggers. Audit integrity, external append-only retention, and attribution remain separate requirements.

The resolver accepts a Controller-issued observation ID and a target reference, reloads the authoritative Target row and observation, compares target identity/platform, recomputes and constant-time compares the raw-payload digest, reparses the versioned schema, checks freshness, rejects superseded observations when `require_latest` is set, and enforces the current target binding generation. For channel-authenticated rows it also checks that the same agent and credential remain active for that binding. It requires expected policy/catalog values to appear in a Controller-owned `SupportedBindingVersions` allowlist and match the persisted observation. Missing version context returns `UNRESOLVED_UNTRUSTED` without an evidence digest; unknown or inconsistent versions are rejected. When versions match, it recomputes `assessment-evidence/v1` through the production binding module, but still returns `UNRESOLVED_UNTRUSTED` and `approval_context=None` because channel authentication does not prove assessment provenance or human authorization. The current assessment route persists null policy/catalog versions because no authoritative assignment is connected to collection; its observations cannot enter a trusted approval-binding path.

The current local models add tables without changing existing Target columns; application startup's `create_all` can add these tables to an existing SQLite database, but it does not migrate changed columns. Unit tests use temporary databases, including a legacy Target-table shape. The Controller's configured `hardening.db` was not opened or changed in this task. Future column changes require explicit versioned migrations and backup/rollback planning.

### 3.10 Local identity lifecycle and transport slice

The identity service is a set of internal lifecycle primitives, not a trusted enrollment workflow. A locally provisioned identity binds a unique agent ID to a unique workload URI. Credential rows contain SHA-256 certificate fingerprints, optional public-key fingerprints/metadata, URI, not-before/expiry and lifecycle status; private keys are never stored in SQLite. Target-agent binding rows have unique generations and at most one active binding per target. Credential activation/rotation, target rebind, identity replacement, revocation and quarantine invalidate active binding records and stale policy assignments. These operations have no authenticated administrative API, device proof-of-possession, issuance authority, or durable pending-approval records to invalidate. The local service is not an authorization boundary until its caller is protected by an approved admin/enrollment design.

The Controller mTLS client loads an explicit CA bundle and Controller certificate/key, validates the configured Controller URI against its own certificate SAN, and uses normal TLS chain and hostname verification. After TLS response headers, it obtains the peer leaf certificate, maps its exact SHA-256 fingerprint to the active credential referenced by the active target binding, checks current identity/credential states and validity, and checks the registered URI SAN. It validates before response content is consumed or stored. The Go listener requires a trusted client certificate and the expected Controller URI SAN. A bad CA, hostname, expiry, credential status, target mapping or identity fails closed. mTLS authenticates workloads on a channel; it does not authenticate an operator, authorize a policy/action, or prove an approval.

Only the read-only status/discovery/assessment/plan listener traffic is intended for this configuration. The agent's execution handlers remain governed by the existing disabled-by-default token check and are not integrated with mTLS identity or approval verification. The current Controller exposes no execute or rollback routes. Do not configure execution credentials or infer production readiness from local ephemeral-certificate tests.

### 3.11 Local policy/catalog registry slice

The registry uses canonical definition contract `policy-catalog-definition/v1`: a bounded JSON object encoded as strict UTF-8 using sorted keys, compact separators, and rejected non-finite numbers; SHA-256 is over the domain prefix plus a NUL byte and those canonical bytes. Records bind platform, policy version, catalog version, provenance reference, definition bytes/digest and explicit verification/applicability/enablement. Registration is always disabled, unverified and unconfirmed. Target assignment captures the active target-agent binding generation. Resolution recomputes the digest and denies stale generation, changed content, disabled/revoked/unverified definitions, unconfirmed applicability, missing assignment, or platform mismatch.

The local working tree now adds protected policy-review routes requiring a separate OIDC role which is unconfigured by default. Approval additionally requires an operator-provisioned exact trust pin for source-evidence digest/reference, definition digest, platform, policy and catalog versions, plus an explicit applicability assertion. Append-only review records capture the authenticated principal, decision, rationale, reviewed digest/scope and timestamp; current definition and current pin are rechecked before assignment/resolution or re-enablement. Review state transitions and policy registration/assignment/revocation emit transaction-coupled audit events. No trust pins or authoritative policy-source ingestion are provisioned, so no production policy is approved. The test pins are fixtures, not evidence. A configured pin is an operator trust assertion; it cannot independently prove source acquisition or applicability. The existing four Ubuntu SSH controls remain a prototype, not formally verified CIS coverage; official benchmark PDF verification and formal ARM64 applicability remain open.

The read-only assessment route now consumes only assignments which pass the registry's active binding/credential and current reviewed-definition checks. For `aha-agent-assessment-policy/v1`, the definition explicitly names platform, OS release, architecture, and ordered control IDs/expected values. The Controller checks the read-only `/discovery` result and exact ordered assessment control IDs/expected values before persisting an observation, annotating it with Controller-derived policy/catalog versions and the definition digest in the response. This is a contract match against agent-reported data, not remote attestation or proof of executable integrity. A successful assessment observation and its sanitized audit event share a transaction; failed validation or audit persistence rolls it back. Test-only fixtures are explicitly labeled test provenance and are not CIS evidence. Loopback HTTP remains unauthenticated; production mTLS deployment and a trusted evaluator/provenance authority are not available. The planner response remains distinct on `/plan`, and no execution or rollback integration exists.

### 3.12 Policy-aware read-only assessment status

The endpoint requires an assigned, enabled, currently reviewed definition with matching current target binding and active credential; otherwise it returns an explicit conflict and makes no agent request. Its definition schema is intentionally limited to target applicability and an ordered control-ID/expected-value contract. Agent-reported `/discovery` data and findings are checked against that contract before an observation is stored. The response distinguishes a successful policy-contract match from whether the agent channel was authenticated. No policy version/digest is copied from agent data. The result is not an independent assessment attestation, CIS compliance claim, approval context, or dispatch authorization. The existing SSH-tunnel path is loopback-only and unauthenticated. Assessment success audit uses a transaction with the observation; audit failure returns service unavailable and rolls back the observation. Denials and failed upstream/result validation are recorded as sanitized `assessment.failed` events and never as `assessment.collected` successes. If failure-event persistence is unavailable, the API returns service unavailable.

### 3.13 Controller audit chain and lifecycle audit coverage

The local working tree implements `security-audit-event/v1` in SQLite. It serializes a canonical event body as sorted compact UTF-8 JSON with UTC microsecond timestamps and computes `sha256:` over `AHA-SECURITY-AUDIT-EVENT\0security-audit-event/v1\0` followed by those bytes. Sequence and previous-event digest bind ordering. A singleton chain head is updated with each event; a SQLite first write serializes concurrent appends. Target registration, enrollment challenge creation/expiry/consumption/revocation, policy registration/assignment/review/rejection/enable/disable/revocation are coupled to the business transaction. OIDC actor issuer/subject are recorded where an authenticated human initiated the transition; challenge consumption/automatic expiry are marked as system-observed without asserting agent identity. Sensitive key names are rejected from metadata and values are size/depth bounded. Append failures cause integrated operations to roll back or fail closed. Temporary-SQLite tests cover concurrent ordering, links, verification, content/removal tampering, secret exclusion and transaction rollback.

This database hash chain is **not immutable** and is not resistant to an attacker with unrestricted database/schema write access: such an actor can alter rows, drop triggers, and recompute the head and chain. It detects ordinary corruption only when compared with a trustworthy checkpoint. Current SQLite triggers block ordinary application update/delete of event/review rows, but there is no external log shipping, independently controlled WORM store, signed checkpoint, retention service, outbox/reconciliation, or complete read/access auditing. This code is a locally tested foundation, not deployed security control or production-grade audit.

## 2. Security objectives and invariants

The future execution path must enforce these invariants at both Controller and agent boundaries:

1. Execution is disabled by default. Missing, stale, or invalid security configuration fails closed. No operator can enable privileged actions by supplying `approved: true` or by knowing a shared bearer token.
2. A network address never establishes target identity. A request is authorized against a stable target ID, its enrolled agent identity, and the current target/agent binding generation.
3. An approval authorizes one exact operation on one exact target, under one policy/catalog version, during a short validity interval, once only.
4. The agent validates authenticated caller identity, signed approval, target/action/parameter bindings, policy constraints, expiry, and replay state before pre-change capture or mutation.
5. Execution is typed and catalog-bounded. There is no arbitrary shell/script/API pass-through. The executor uses the least operating-system privilege that can perform the specific action.
6. State capture and the required pre-execution audit event are durable before mutation. Any uncertain outcome is reconciled; it is never blindly retried.
7. Verification is independent of the command's exit status. Failure invokes bounded recovery; recovery failure is surfaced and blocks further actions on that target pending reconciliation.
8. Rollback is a separate privileged operation requiring its own authenticated, action-bound, target-bound approval. It validates the exact recovery snapshot and records its own audit lifecycle.
9. The remediation-validation sandbox and attacker/decoy sandbox have separate networks, identities, credentials, and control planes. A decoy cannot access target-control APIs, approval signing keys, agent credentials, or privileged target networks.
10. No platform is supported by implication. Each platform/control set has explicit applicability, tested adapter behavior, and its own evidence level.

### 3.1 Agent identity, enrollment, and lifecycle

**Identity model.** Keep separate identifiers for: (a) the Controller's stable `target_id`, (b) an agent's stable `agent_id`, (c) an enrollment/binding generation, and (d) network addresses. Assign IDs server-side or from a cryptographically random UUID source. Enforce unique constraints for `agent_id`, active credential serial/public-key fingerprint, and the active target-to-agent binding. A target reassignment increments a binding generation and invalidates approvals, sessions, and queued work tied to the prior generation. Never use a hostname, IP address, display name, MAC address, or self-reported `agent-dev` value as the authenticated identity.

**Enrollment flow.** An authenticated administrator creates a pending enrollment bound to one target ID, expected platform/scope, expiry, and one-time enrollment nonce. The agent creates its private key locally and sends a certificate signing request or obtains a workload identity through the selected issuer. The enrollment service verifies the one-time nonce, target assignment, key possession, and administrator authorization before issuing credentials. The agent's first authenticated check-in proves possession of the issued key and confirms its target/agent/binding-generation tuple. Consume the enrollment nonce atomically; reject duplicate enrollment, unexpected key replacement, expired bootstrap authorization, and identity collision. Do not treat a successful TLS handshake as permission to remediate.

**Credential issuance and storage.** Prefer an existing enterprise PKI or workload identity service over custom issuance. Evaluate SPIFFE/SPIRE X.509-SVID and Workload API for short-lived workload credentials and managed trust bundles; the X.509 profile places SPIFFE identity in a URI SAN and uses X.509 path validation. Compare that operational model with the organization's existing private CA/device management, especially where edge devices cannot reliably reach a workload API. The agent private key should be generated on the device and remain non-exportable where a TPM, secure element, or operating-system keystore is available; document the weaker storage fallback for unsupported devices. The Controller stores public certificate/key metadata and target bindings, never private agent keys.

**Rotation, revocation, and replacement.** Use short-lived certificates with automatic renewal and a narrow, monitored overlap window. Support immediate revocation and quarantine on suspected compromise, lost device, target reassignment, or decommission. Define revocation distribution and maximum stale-cache age; if revocation state cannot be checked within policy, privileged requests fail closed. Replacement creates a new key and binding generation, revokes the old credential, cancels pending approvals/jobs, and records old/new fingerprints and operator identity. Keep retired public certificates and signed audit evidence long enough to validate historical signatures. Credential rotation must not silently transfer pending approvals. Avoid making certificate subject reuse alone sufficient for a new agent to inherit authorization.

**Identifier uniqueness and collision handling.** Use a unique database constraint plus transaction-level conflict handling. Duplicate IDs, cloned credentials, conflicting active target bindings, or unexpected key changes enter quarantine and require an authenticated recovery procedure. A cloned VM/image must not inherit an active agent private key or enrollment token. Reimaging/replacement needs explicit decommission/re-enrollment and a new generation.

### 3.2 Authenticated transport and trust roots

Use TLS 1.3 where supported, with TLS 1.2 only where an explicit compatibility policy requires it. Follow normal X.509 chain validation and hostname/SAN verification. The Controller must validate that the server certificate chains to the configured private trust roots **and** that its authenticated identity maps to the target's enrolled agent; never set `verify=False`, accept arbitrary certificates, disable hostname checks, or fall back to HTTP after a TLS failure. The agent must authenticate the Controller service identity before accepting execution requests. Use distinct server and client identities and purpose-specific trust roots where the PKI supports that separation.

**Mutual authentication.** Mutual TLS is the preferred candidate for the Controller-agent service channel when both sides can hold managed certificates. Require client certificates on privileged routes, map the validated SAN identity to an authorized Controller workload, and bind authorization tokens/claims to that peer identity where supported. TLS authenticates workloads and protects the channel; it does not authenticate the human approver or by itself authorize an action. If mTLS is unavailable in a specific managed environment, select a reviewed alternative such as short-lived, audience-restricted, sender-constrained OAuth tokens under RFC 9700/RFC 8705; do not use a long-lived shared bearer secret as a production substitute.

**Trust roots and certificate verification.** Provision trust roots through managed configuration, not request data or arbitrary agent response fields. Define root ownership, pin/distribution strategy, renewal/overlap, revocation, compromise response, and audit. Check certificate validity, critical extensions, key usage/EKU, expected SAN identity, and chain constraints. Fail closed on unknown roots, hostname/SAN mismatch, revoked/expired certificate, TLS downgrade, or unavailable revocation data beyond the permitted freshness window. Separate Controller-to-agent roots from user identity-provider roots and from sandbox roots.

**Current client changes required later.** The current Python `httpx.get` path has no client certificate configuration and its default URL is HTTP. Future work must use explicit `ssl.SSLContext`/CA bundle and client certificate configuration, with verification enabled, and reject non-loopback plain HTTP for all privileged paths. Agent `net/http` will need an explicit reviewed TLS listener/proxy deployment. A normal HTTPS URL in the current override is not sufficient proof of identity binding.

**Lab SSH tunnel constraints.** Retain the existing tunnel only as a development/read-only lab path: Controller and agent HTTP endpoints remain loopback-bound; SSH host key verification is enabled and the expected host key is pinned; SSH access uses a named, least-privilege lab account and short-lived access; the forwarded port is not exposed to other interfaces; no execution token or privileged operation is used; tunnel logs and lifetime are controlled. The tunnel is not an enrollment mechanism, mTLS replacement, approval channel, or production security acceptance. If used for any future privileged sandbox test, it requires a separately approved test procedure and must not be confused with production transport.

### 3.3 Authenticated human identity and trusted approval

**Human authentication.** A local API bearer-token validator and configured role dependencies now protect target management/read routes and enrollment-challenge management, but there is no selected/deployed OIDC provider or browser login/session flow. Before production use, integrate the organization's existing provider and evaluate Authorization Code flow with PKCE, state/nonce validation, MFA/step-up policy for privileged approvals, secure session cookies, CSRF protection, and server-side role mapping. Persist immutable provider issuer + subject as requester/approver identity; an email or display name alone is not an identity key. Identity-provider authentication establishes who acted; Controller policy determines whether that person may request or approve this target/action. Require separation of duties for high-impact actions where policy calls for it.

**Immutable approval subject.** The Controller first creates and stores an immutable proposed operation derived from a versioned plan. It contains:

- unique `request_id` and approval `jti`/nonce;
- stable `target_id`, `agent_id`, and target-agent binding generation;
- exact action ID, typed parameters, and canonical parameter digest;
- complete plan digest, assessment/evidence reference and digest;
- policy ID, policy version, catalog version, and policy-content digest;
- requester identity, approver identity, approval role, decision, and approval timestamp;
- `not_before`, short `expires_at`, status, and intended operation (`execute` or `rollback`);
- for rollback: the original execution ID and exact recovery-state manifest digest;
- issuer/key ID, intended agent audience, and required policy constraints.

The approver UI displays the target identity and binding, platform, exact action and human-readable parameters, expected impact, policy/catalog version, evidence summary, rollback/recovery plan, and expiry. The approval decision is recorded against that immutable object. Any change to target, agent generation, action, parameters, policy/catalog, evidence basis, or rollback snapshot invalidates the approval and requires review again.

**Integrity-protected approval.** The Controller approval service issues a signed, short-lived JWS approval envelope only after an authenticated approver is authorized and the approval record is durably committed. Evaluate JWT/JWS under RFC 7515/7519 and JWT best current practice RFC 8725. The envelope includes issuer (`iss`), exact agent audience (`aud`), request/approval ID (`jti`), issue/not-before/expiry (`iat`/`nbf`/`exp`), target ID, agent ID and binding generation, operation type, action ID, canonical parameter digest, plan digest, policy/catalog identifiers and digests, approver subject, and original execution/state digest for rollback. Sign with a dedicated approval-signing key protected by a managed KMS/HSM or equivalent, separate from TLS keys and agent keys. Publish verification keys through an authenticated configuration channel and support controlled `kid` rotation/overlap/revocation.

Use an allowlisted signature algorithm and key type, validate the exact issuer and audience, reject unknown/duplicate claims and unexpected token types, and never follow an untrusted `jku`/`x5u` key URL. The isolated Go verifier selects jwx/v4 v4.5.0 as recorded in Section 7. The local Controller bearer validator uses pinned PyJWT/cryptography with RS256/ES256 allowlisting and explicit key checks; its IdP deployment/configuration, operational key rotation, role semantics, and production security review remain outstanding. Approval issuance must be evaluated separately and may use a KMS-backed signer rather than exporting a private key to application memory.

**Implemented digest contract for the isolated verifier.** `planner.Action` is encoded as bytes, not language-specific JSON. The exact v1 byte sequence is: ASCII bytes `AHA-PLANNER-ACTION-DIGEST`, then NUL, ASCII `planner-action/v1`, then NUL; then six strings in this order: `action_id`, `control_id`, `title`, `action_type`, `current_value`, `desired_value`; then `risk_score`; then `execution_mode`; then `reason`. Each string is strict UTF-8 (no Unicode normalization is performed) preceded by its byte length as an unsigned 32-bit big-endian integer. `risk_score` is the IEEE-754 binary64 bit pattern in big-endian order. SHA-256 is applied to the complete sequence and rendered as lowercase hexadecimal with the `sha256:` prefix. Empty `current_value` is encoded as a zero length; invalid UTF-8, non-finite/negative scores, and incomplete required fields are rejected. This fixed schema and field order do not depend on JSON object ordering, float-to-text formatting, or language serialization.

The same golden vector in `agent/internal/approval/testdata/action_digest_v1.json` is checked by the Go implementation and the Controller's Python production implementation via tests; both assert exact canonical bytes and SHA-256, including non-ASCII UTF-8 and a fractional score. It covers this precise Go `planner.Action` representation, not the full approval envelope or a production issuer. The Controller must preserve field values/types. The digest binds every field in the current action struct; target ID, agent ID/binding generation, operation, and policy/catalog versions are separate context.

**Implemented feature-off composite binding contracts.** The Go baseline defines `assessment-evidence/v1`, `plan-binding/v1`, and `recovery-manifest/v1` in `agent/internal/approval/bindings.go`; the current working tree's Python production module implements the same schemas. All use SHA-256 and lowercase `sha256:<64 hex>` output. They use explicit fixed field order and big-endian binary primitives; they do not serialize Go/Python maps or use default JSON. Each canonical sequence begins with its domain ASCII string, NUL, the version ASCII string, NUL. Each string is strict UTF-8 (no Unicode normalization is performed), encoded as a 4-byte unsigned big-endian byte length followed by bytes. Contract strings are limited to 1 MiB, aggregate canonical bytes to 4 MiB, and each repeated collection to 4096 items. Counts are uint32 big-endian. Times are signed int64 Unix seconds in two's-complement big-endian form followed by uint32 big-endian nanoseconds. A digest embedded inside another canonical sequence is its raw 32 SHA-256 bytes, not prefixed text.

- **`assessment-evidence/v1` field order:** `assessment_id`, stable `target_id`, `source`, `catalog_version`, assessment `platform`, `collected_at`; uint32 finding count; for each finding in existing order: `control_id`, `title`, `status`, `applicability`, `severity`, `current_value`, `expected_value`, `message`, `source`; uint32 evidence count; each evidence item in existing order as `name`, `value`, `source`; then one byte for error presence (`0` absent, `1` present) and, if present, `code`, `message`, `source`. This includes every field of the current assessment/finding/evidence/error structs. Current `assessment.Assessment` has no assessment ID, target identity, collection time, source envelope, or catalog version. These are explicit `EvidenceProvenance` values and must be created and retained by a trusted assessment workflow; fabricated or token-sourced provenance defeats the intended binding. This digest does not attest that the assessment was honestly collected.
- **`plan-binding/v1` field order:** stable `target_id`, operation (`execute` or `rollback`), policy version, catalog version, plan status, plan platform; raw 32-byte `assessment-evidence/v1` digest; uint32 action count; then one raw 32-byte `action-digest-v1` digest per action in exact `planner.Plan.Actions` order. Empty plans are valid; every present action binds every current `planner.Action` field. The expected target and evidence target must match; plan/evidence platforms and catalog versions must match. Changing target, operation, policy/catalog version, status/platform, evidence, action or action order changes the digest.
- **`recovery-manifest/v1` field order:** stable target ID, agent ID, binding generation, original execution ID, state action ID; raw 32-byte action digest; execution-state capture time; previous effective value; recovery file path; one-byte existence marker; uint32 mode; file capture time; when present, raw 32-byte SHA-256 of file content and uint64 content length. For an absent file, the digest bytes and size are all zero. The implementation recomputes and checks `FileState.ContentSHA` before hashing, and rejects inconsistent absent-file state or invalid mode. It binds exact path, existence, mode, content identity/size and the available capture times. The current `FileState` has no owner/group, inode, ACL or extended-attribute fields; this version does not claim to bind metadata the type does not capture. `ExecutionState` has no execution ID, so a trusted caller must resolve supplied `ExecutionID` against authoritative execution/audit records. Any future schema changes require a versioned successor and vectors.

`agent/internal/approval/testdata/approval_bindings_v1.json` is shared by Go and Python; both production implementations reconstruct all three byte sequences and their tests check exact bytes and SHA-256. Go tests cover binding mutation/corruption; Controller tests cover mutations for target, source/catalog, assessment content, ordered action, action parameter and policy, plus stale/replaced/mismatched provenance and corrupt inputs. These tests establish encoding compatibility and local validation only. They do not establish that caller inputs are authoritative or implement issuance, durable approval/replay records, human authorization, or runtime use.

The isolated verifier now requires `plan_digest` and `evidence_digest` for an `execute` envelope, and `recovery_manifest_digest` for a `rollback` envelope. `Config` receives the expected plan/evidence or recovery-manifest objects and the verifier recomputes their digests; it rejects a blocked plan and requires the expected action digest to occur in the bound READY plan. It also checks rollback manifest target, agent, generation and action against the verifier context. Cross-operation binding claims are rejected. These inputs must still be supplied from authoritative Controller/agent stores by a future trusted caller; a token-provided digest is never an expectation source. The Python issuer is not implemented. Cross-language encoding is tested, but this is not a complete Controller-agent integration contract because authoritative provenance and issuer behavior are outstanding.

For future typed operation schemas, version the byte format and share cross-language golden vectors before changing either side. RFC 8785 JSON Canonicalization Scheme (JCS) remains a candidate only if a later schema deliberately chooses canonical JSON and meets its numeric/data constraints. Reject ambiguous duplicate JSON keys, unknown parameters, numeric coercion, and non-canonical representations at the envelope/request boundary.

**Agent verification sequence.** Before any state change, the agent must: (1) validate the TLS peer and Controller identity; (2) verify JWS using the configured approval issuer key and allowed algorithm; (3) validate issuer, audience equals this enrolled agent, target ID and binding generation equal locally provisioned identity, action and typed parameters are supported, expected action/plan/evidence/recovery digests match, current policy permits it, and `nbf`/`exp` are valid under bounded clock skew; (4) check approval/request status and revocation policy; (5) atomically reserve/consume the `jti` and idempotency key in durable storage; (6) persist the required audit intent and state-capture intent; only then may execution proceed. `approved: true` is ignored or rejected by a future contract and is never an authorization input. A copied signed envelope is not sufficient: mTLS identity, exact audience/binding, short expiry, and durable one-time consumption are all required.

### 3.4 Target/action binding, expiry, replay, and idempotency

Binding is to stable IDs and immutable digests, not a display label or IP. A signed request is valid only for the `target_id`, currently enrolled `agent_id`, binding generation, operation type, action ID, exact canonical parameters, policy/catalog/evidence digests, and intended audience stated at approval. Reassignment or replacement increments the binding generation and invalidates old approvals. The agent must compare the authenticated local target/agent binding with the approved values; a caller cannot override them in the payload.

Set a short expiry according to operator workflow and target connectivity (initial proposal: five minutes, configurable only through reviewed policy); do not extend an approval because of a retry or network delay. Define a small maximum clock skew, require synchronized clocks, reject when skew exceeds it, and never accept `exp` omission. Expiration, revocation, policy change, target reassignment, or agent replacement invalidates an unconsumed approval.

**Durable replay/idempotency stores.** The Controller database needs transactionally unique `request_id`, `jti`, and `(target_id, idempotency_key)` records with action digest and state transitions. The agent needs a durable local replay journal protected from the agent's unprivileged account and bound to its target identity. On first use, atomically record `jti`, request ID, digest, state, and timestamp before mutation. A duplicate with the same request ID and digest returns the persisted prior status/result; the same ID with a different digest is a conflict and is denied. A new ID presenting an already consumed `jti` is denied. Reservations have explicit states (`issued`, `reserved`, `captured`, `executing`, `verified`, `recovery_required`, `completed`, `denied`) and are never reset to unused after a crash.

The Controller consumes/reserves approval state before dispatch; the agent independently consumes the signed approval before execution. This two-sided ledger handles delivery retries and cloned/restarted processes. If Controller state says dispatched but the agent receipt is unknown, reconcile by request ID; never mint a replacement automatically. If the agent has consumed approval but outcome is unknown, inspect the journal and target state, complete verification or recovery, then require a fresh approval for any new operation. Exactly-once delivery across a network is not assumed; idempotent state transitions and safe reconciliation are required.

### 3.5 Policy authorization and least privilege

Authorization has separate decisions for requester, approver, Controller service, target agent, and operating-system executor. Use default-deny RBAC/ABAC with scoped role grants: organization/project, target set, platform/control set, action risk, environment, and time. Requester and approver may need to be distinct. Enforce policy in the Controller before presenting an approval and again in the agent immediately before execution; an approval cannot override a newer deny, unsupported platform/action, changed policy version, revoked identity, or emergency kill switch.

The action registry is typed and allowlisted. Each action specifies supported platform/version/architecture, parameter schema/ranges, preconditions, state capture, privilege set, verification, recovery procedure, timeout, idempotency behavior, and policy/catalog version. Unknown action IDs, parameters, platform/version, incomplete assessments, unknown applicability, stale evidence, unsupported policy, unavailable authorization service, invalid claims, or audit dependency failure deny the operation. Do not provide arbitrary command strings, shell fragments, file paths, or URLs from the Controller. Validate all paths against action-owned fixed paths and reject path traversal/symlink substitution.

Keep execution off by default in code and deployment configuration. The future feature gate must be explicitly enabled only after all release gates pass, and still require a valid end-to-end authorization. The current unset-token guard remains as a fail-closed prototype gate; do not configure `AGENT_EXECUTION_TOKEN` as a shortcut or treat it as the future authorization system. Use a narrow privileged helper or platform-specific service account with only the exact permissions required; do not run the full agent as root. Separate read-only assessment privileges from remediation privileges. Never elevate the Controller or decoy sandbox to target privilege.

Safe denial returns a generic request/error identifier to callers, preserves detailed reason only in protected audit/evidence, does not disclose credentials, signing material, recovery contents, or internal paths, and performs no executor call. Rate-limit authentication/enrollment failures and alert on repeated suspicious denials. An authorization or audit service outage is a denial, not a bypass or a fallback to plaintext/shared token.

### 3.6 State capture, execution, verification, recovery, and rollback

Before mutation, capture the exact pre-change state, effective configuration, relevant metadata/permissions, target identity, action digest, request ID, and timestamp. Persist a root/administrator-protected recovery manifest containing the allowed fixed paths, existence/content/metadata digests, action ID, target/agent/binding generation, original approval/request ID, and executor version. Integrity validation must reject unknown fields/actions, path escape, symlink substitution, digest mismatch, wrong target/generation, stale state, and unauthenticated modification. Protect snapshot confidentiality as well as integrity. Prefer a signed manifest with an agent identity key or a reviewed local integrity mechanism backed by OS access control; signing does not replace access control or audit.

Execute one bounded operation under a timeout and resource limit. Do not accept or construct arbitrary shell commands from request data. Record start and terminal states around each step. A timeout, interruption, process restart, or lost response makes the result `unknown/reconciliation-required`, not automatically failed-and-retryable. Re-read effective system state after the operation using an independent check path; compare to expected policy outcome, not only the command's return code. Persist verification evidence and references.

If execution fails or verification is not satisfied, run only the action's pre-reviewed automatic recovery procedure using the captured manifest, then independently verify restored state. If recovery fails, stop further mutation for that target, mark `recovery_required`, alert an operator, preserve evidence, and require manual review. Do not report success or silently suppress an uncertain rollback.

Rollback is a distinct typed operation with a fresh approval and signed envelope. It must bind the target/agent generation, original execution ID, exact recovery manifest digest, rollback parameters, policy version, approver, expiry, and unique one-time request ID. It must validate the snapshot before restore, restore only approved paths/state, verify file/effective system state independently, and produce a separate audit lifecycle. A failed rollback verification leaves the target quarantined from additional automated changes and raises an operator alert.

### 3.7 Audit and evidence requirements

Create append-only, access-controlled audit events for enrollment/credential lifecycle, human authentication and authorization decisions, plan creation/change, approval issue/approve/revoke/expire, request dispatch, agent authorization, state capture, execution steps, verification, recovery, rollback, denials, and audit outages. Each event includes at least:

- event ID, event schema version, timestamp and clock source;
- authenticated requester and approver provider issuer/subject, roles, and decision (or service identity for non-human events);
- stable target ID, agent ID, binding generation, and authenticated certificate/key fingerprint;
- request ID, idempotency key, approval ID/nonce, approval issue/approval/expiry times, and approval key ID;
- operation type, action ID, canonical parameter/action digest, plan/assessment/evidence references, policy/catalog version and content digest;
- authorization decision and policy decision reference;
- executor build/version, state-capture manifest reference/digest, execution outcome, timestamps, timeout/interruption state;
- verification result and evidence references; automatic recovery/rollback attempts, results, and verification; and correlation IDs for event pipeline/dashboard.

Never record bearer values, private keys, raw approval secrets, unnecessary personal data, or sensitive recovery contents. Store protected evidence separately and link by immutable reference/digest. Restrict read/export/delete privileges; define retention, legal hold, access review, and backup/restore. Operators must be able to detect tampering and correlate records across Controller, agent, and executor.

Evaluate a managed immutable/WORM audit or evidence service with signed checkpoints and independent retention controls before implementing a custom event store. RFC 9162 Certificate Transparency provides an append-only Merkle-log model worth evaluating for inclusion/consistency proofs, but is a certificate-transparency protocol and should not be repurposed as an application audit system without a reviewed design. Do not invent a home-grown hash-chain or signature protocol. A transactional outbox can couple Controller decisions to durable audit publication; independently verify delivery and retention.

**Audit failure behavior.** Before execution, if the durable approval, replay reservation, state-capture intent, or pre-change audit event cannot be persisted and acknowledged, deny before mutation. If audit storage fails after an operation has started, stop new operations, finish only the minimum verification/recovery needed to leave the target safe, write to a protected durable local pending-event spool, mark the result incomplete, and block subsequent execution until reconciliation confirms central audit ingestion. Do not claim a complete success record or discard local evidence. Alert on audit outage and test recovery of the queue. If local durable storage also fails, perform no new mutation; for an in-flight operation, follow its pre-approved safe recovery path and report an unresolved incident through the out-of-band operator channel.

### 3.8 Separate sandbox trust boundaries

**Remediation-validation sandbox:** disposable target images/VMs/containers and test agents live in an isolated network and account. It may use synthetic credentials and a sandbox-only Controller/CA/approval key. It must have deterministic reset/snapshot, bounded privileges, egress allowlists, failure injection, and no route or credential path to production targets. Sandbox approvals and credentials are rejected by production trust roots. Test real state capture, interrupted actions, verification, recovery, and rollback here before separately approved live tests.

**Attacker/decoy sandbox:** Cowrie/OpenCanary workloads and attacker-facing infrastructure use a distinct account, network, identities, storage, and secrets. They receive no agent enrollment token, Controller service credential, approval signing key, target SSH key, privileged API route, or production trust bundle. Firewall/IAM policy must deny decoy-to-Controller execution and decoy-to-target connectivity. Send only sanitized, one-way event data to a separately authenticated event ingestion boundary; event ingestion must not become a command/control path. Validate containment and credential absence, including after container escape assumptions.

The two sandboxes are separate systems with separate threat models and test evidence. A decoy is not a remediation test target, and remediation tests must not be run on an attacker-facing decoy.

## 4. Threat model

### Assets

Agent and Controller private keys; target/agent bindings; human identity and roles; approval-signing keys and records; policy/catalog and evidence integrity; execution and recovery state; audit history; target availability/configuration; sandbox credentials and network boundaries; event data and dashboard access.

### Adversaries and assumptions

Consider an unauthenticated network attacker, stolen agent or Controller credential, compromised target host, compromised Controller/API account, malicious or mistaken authorized operator, insider with partial database/storage access, replaying proxy or queue, cloned/reimaged agent, compromised dependency/build pipeline, and attacker who escapes or pivots from the decoy sandbox. The design assumes standard cryptographic primitives and TLS implementations are correctly maintained, signing keys remain protected, and host-level compromise of the target can defeat local agent controls; that risk requires isolation, detection, recovery, and operator response rather than a claim of prevention.

### Threat-to-control mapping

| Threat | Required controls | Residual risk / response |
|---|---|---|
| Stolen agent credential or private key | Non-exportable key where available, short-lived certificate, mTLS identity mapping, revocation/quarantine, target binding generation, least privilege, audit | Host compromise may expose software-held keys; revoke, replace, investigate, and invalidate pending approvals |
| Unauthorized Controller/API caller | OIDC authentication, role/target/action policy, CSRF/session protections, service mTLS, default deny, rate limits | IdP/Controller compromise remains high impact; isolate, revoke sessions/keys, preserve audit |
| Forged or stolen approval | Dedicated signing key, strict JWS validation, issuer/audience/agent/target/action/policy binding, mTLS, short expiry, single-use durable `jti` | Approval signer compromise requires key revocation, pending approval cancellation, incident response |
| Expired approval / clock manipulation | Required `exp`/`nbf`, bounded skew, monitored time, no retry extension | Clock loss or out-of-policy skew denies operation |
| Replay or duplicate delivery | Controller and agent atomic replay ledgers; idempotency key bound to digest; state reconciliation | Ambiguous crash outcomes require reconcile and fresh approval, not blind retry |
| Wrong target or DNS/address substitution | Stable target/agent IDs, cert SAN identity, local enrollment binding generation, TLS hostname and SAN checks | Routing error is denied when identity does not match; network policy still required |
| Changed action/parameters/evidence/plan/recovery state after approval | `action-digest-v1`, `assessment-evidence/v1`, `plan-binding/v1`, and `recovery-manifest/v1` canonical recomputation against trusted expected objects | Target, action order/parameter, evidence, policy/catalog, state digest/path/mode mismatch denies before mutation; a changed recovery content hash is rejected |
| Bad, expired, revoked, or wrong-host certificate | Normal TLS chain, SAN/hostname, EKU, trust-root and revocation checks; no insecure fallback | Revocation service outage beyond freshness budget denies privileged requests |
| Interrupted execution / agent restart | Durable step journal, pre-captured state, no automatic repeat, reconcile by request ID, verify/recover | Target may require operator intervention; quarantine further actions until safe |
| Invalid/corrupt recovery state | Protected snapshot store, strict path/action/target checks, digest/signature validation, reject unknown schema | Deny restore; preserve evidence and require manual recovery |
| Failed audit write | Pre-change durable audit gate; protected local pending spool for in-flight case; block new actions, alert, reconcile | Unrecoverable local/central failure means incident and no success claim |
| Rollback verification failure | Separate approval, integrity-checked snapshot, independent verification, target quarantine | Human incident response and manual recovery required |
| Decoy compromise/pivot | Separate account/network/trust roots, no credentials or control APIs, egress/ingress controls, sanitized one-way telemetry | Escape remains possible; segmentation limits blast radius and containment tests verify it |
| Malicious/compromised dependency or build | Pinned/reviewed dependencies, SBOM, signed artifacts, provenance, reproducible build where feasible, update authorization | Supply-chain compromise remains; revoke artifacts/credentials and incident response |

## 7. Standards and implementation candidates to evaluate

These are candidate references, not claims that the repository uses them or blanket endorsements of a particular deployment:

- TLS 1.3: [RFC 8446](https://www.rfc-editor.org/rfc/rfc8446); X.509 path validation: [RFC 5280](https://www.rfc-editor.org/rfc/rfc5280); mutual TLS/certificate-bound tokens: [RFC 8705](https://www.rfc-editor.org/rfc/rfc8705); OAuth security guidance: [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700). mTLS gives workload identity and channel protection but adds CA/rotation/availability work and does not authenticate a human or convey action approval by itself.
- Workload identity: [SPIFFE X.509-SVID](https://spiffe.io/docs/latest/spiffe-specs/x509-svid/) and [SPIFFE Workload API](https://spiffe.io/docs/latest/spiffe-specs/spiffe_workload_api/), with SPIRE as one possible implementation. This can standardize short-lived workload identities and bundle rotation, but adds a control plane and may be unsuitable for disconnected edge hosts; compare with existing enterprise PKI/device management.
- Human identity: OpenID Connect over OAuth 2.0 Authorization Code + PKCE and the organization's existing IdP; use [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700) security guidance. This reuses enterprise authentication and MFA but requires correct session, CSRF, role, and provider lifecycle integration.
- Approval integrity: [JWS RFC 7515](https://www.rfc-editor.org/rfc/rfc7515), [JWT RFC 7519](https://www.rfc-editor.org/rfc/rfc7519), [JWT BCP RFC 8725](https://www.rfc-editor.org/rfc/rfc8725), and [JCS RFC 8785](https://www.rfc-editor.org/rfc/rfc8785). JWS provides a standard signed envelope and registered issuer/audience/time/ID claims; it does not make an approval trustworthy without authenticated approver records, strict validation, target/action binding, and replay storage. JCS adds implementation and data-model constraints; evaluate whether typed deterministic serialization is simpler.
- Go TLS: standard library [`crypto/tls`](https://pkg.go.dev/crypto/tls) and `crypto/x509`; Python HTTP client: [HTTPX SSL configuration](https://www.python-httpx.org/advanced/ssl/) using an explicit verified `ssl.SSLContext`. Standard libraries reduce third-party protocol surface but still require careful trust-root, SAN, client-certificate, and rotation configuration.
- JOSE selected for the isolated Go verifier: [`github.com/lestrrat-go/jwx/v4 v4.5.0`](https://github.com/lestrrat-go/jwx/tree/v4.5.0), using ES256 only. Its module declares Go 1.26.0, compatible with the agent's Go 1.27.1, and its license is MIT. The v4.5.0 release fixes [GHSA-4cf7-xm37-g63h](https://github.com/lestrrat-go/jwx/security/advisories/GHSA-4cf7-xm37-g63h), affecting v4 versions earlier than 4.5.0. This scoped source/version/advisory review is not a general security review or guarantee against other or future advisories. The verifier accepts only ES256 with configured P-256 public keys; it never trusts token-provided keys or fetches token-provided URLs. Python OIDC/JOSE integration is a separate decision and requires its own review.
- Immutable audit: managed append-only/WORM audit or evidence service with separate administrative control and signed checkpoints. [RFC 9162](https://www.rfc-editor.org/rfc/rfc9162) is a Merkle transparency-log reference for append-only/consistency proofs, not a drop-in application audit product. Prefer an established service or reviewed standard implementation over a custom cryptographic log.

## 8. Current decision

**Remote privileged execution is not approved.** Existing live evidence covers only read-only Ubuntu status, assessment, and plan through a local SSH tunnel. Current local code adds identity/binding lifecycle primitives, optional verified mTLS read-only transport, policy/catalog records and review routes, generation-aware observation resolution, OIDC management bearer validation/RBAC, one-time pending enrollment challenges, and a transactional SQLite audit hash chain, but none of the local trust additions is deployed to the live target. The four-control Ubuntu prototype is not formally verified. A deployed IdP/session policy, authenticated agent proof-of-possession and credential issuance/rotation/revocation, production PKI and revocation service, independently verified policy-source review, authenticated assessment provenance, trusted human approval issuance/role authorization, durable replay storage, externally protected audit/checkpoints/retention, and executor integration remain absent. The approval verifier and canonical binding implementations remain disconnected from all execution handlers. `AGENT_EXECUTION_TOKEN` remains unset, no Controller execute/rollback APIs exist, and no live privileged action has been performed. Next dependencies are reviewed OIDC deployment/session policy plus authenticated enrollment/credential authority and independently verified policy definitions, followed by durable replay storage and external audit protection, then a security-reviewed approval-to-executor integration; live execution remains separately gated.
