# ADR-001: Ubuntu SSH privileged-helper boundary

- **Status:** Prototype decision; production deployment is blocked.
- **Date:** 2026-10-23
- **Scope:** Ubuntu action `ACT-SSH-5.1.20` (`PermitRootLogin no`) only.

## Context and current trust state

The normal Go agent is intended to run unprivileged. The existing assessment-only sudo rule permits only `/usr/sbin/sshd -T`; it does not grant executor permissions. The current executor requires root and directly writes `/etc/ssh/sshd_config.d/99-autonomous-hardening-agent.conf`, stores its recovery snapshot under `/var/lib/autonomous-hardening-agent/state`, validates with `/usr/sbin/sshd -t`, reloads `ssh.service`, and checks the effective value with `/usr/sbin/sshd -T`. It verifies the effective value and attempts recovery on failure, but its root requirement is not an acceptable deployment boundary.

`agent/internal/approval` verifies a bounded ES256 compact envelope against an explicitly configured issuer, audience, `kid`/P-256 key map, agent, target, binding generation, operation, action, policy/catalog, time window and operation-specific plan/evidence or recovery-manifest digests. Existing v1 binding functions recompute action, plan, evidence and recovery digests from typed data. The verifier does **not** issue approvals, authenticate a human, validate the human's role, establish that the issuer made a legitimate approval decision, or consume JTI/replay state. Its expected values are only as authoritative as the caller that supplied them.

Controller OIDC authenticates management requests when fully configured, but no agent execution-approval issuance service, trusted approval signing-key deployment, target approval record/role decision, durable execution replay ledger, or audited agent-dispatch path exists. The Controller's SQLite audit chain is locally tamper-detecting but can be rewritten by a database-level attacker and is not an agent-accessible durable audit sink. Agent mTLS currently deliberately filters to read-only GET routes. No trust claim is made for the caller-provided `approved` boolean.

## Decision

Keep the ordinary agent and privileged helper as separate OS principals. A future small helper/service may run with the narrow OS rights needed for this one fixed action; the network-facing unprivileged agent must not run as root. The helper must not be a generic root command runner and accepts no executable, shell string, arbitrary path, service name, or free-form action parameters. Its only permitted filesystem target is the fixed SSH drop-in above; recovery data belongs in a root-owned private directory below `/var/lib/autonomous-hardening-agent/state`, with directory mode `0700`, snapshot mode `0600`, regular-file/no-symlink validation, exact path/action binding and digest verification. Its only permitted system operations are fixed `/usr/sbin/sshd -t`, fixed `/usr/sbin/sshd -T`, and a fixed `systemctl reload ssh.service`. The existing `99-` drop-in is not guaranteed to override earlier directives; `sshd -T` decides whether the intended value is effective. A mismatch requires restoration and independent effective-state verification.

The request is a bounded strict JSON record containing request ID, operation, fixed action ID and compact approval token. All fields are untrusted. Unknown and duplicate members, trailing JSON, malformed input and oversized bodies are rejected. The request cannot supply keys, target identity, binding generation, action parameters, plan/evidence, recovery state, paths, commands, policy, or approval identity. Those are loaded by a trusted future dispatch/configuration layer from controller-owned records and protected local configuration. The helper recomputes v1 digests from expected typed plan/evidence or recovery-manifest data, then calls the existing approval verifier using a trust key map provisioned out of band. It checks the verified claims against the same expected target, agent, generation, operation, fixed action, policy/catalog and recomputed digest context before reserving replay state.

The isolated Go package added in Batch C is a prototype library, not an installed helper process, service, listener, sudo rule, or startup dependency. It defaults disabled, accepts an injected verifier/store/audit/operation, and is not connected to `/execute`, `/rollback`, Controller routes, or the read-only mTLS listener. Tests may explicitly enable it with ephemeral P-256 keys and disposable filesystem state. No such keys or enablement are used by production startup.

## Replay, transaction and interruption behavior

Before invoking the operation callback, the prototype atomically creates a private replay reservation keyed by a digest of JTI using exclusive file creation, writes only a schema, JTI and compact-token digest, fsyncs the file and directory, and rejects duplicates. Same-JTI/same-request retries are denied as replay; same-JTI/different-token requests are denied as conflicts. A reservation is never deleted or reset to unused. A crash after reservation but before a durable outcome leaves an ambiguous reserved request; it must not be retried. An operator must reconcile target and recovery state and obtain a fresh approval/request after resolving the incident. The file store is a tested local primitive, not yet a production root-owned/anti-tamper journal; a managed helper deployment needs a protected durable store and explicit recovery state machine.

After reserving and before invoking the callback, the helper requires the injected audit sink to durably acknowledge an `action.started` event. Failure denies mutation while leaving the reservation spent. After the operation, it records a sanitized outcome event. If this append fails after an operation started, the helper returns an explicit incomplete-audit outcome and error, never `VERIFIED`; the reservation remains spent. The interface defines the required synchronous durable-ack contract, but Batch C does not implement or connect a Go audit sink, external immutable service, or local pending-event spool. Production use is therefore disabled until those exist. Executor errors are surfaced as incomplete/recovery-required; the helper does not infer safe recovery from error text.

The current prototype requires a configured action callback. The callback must be a fixed typed adapter to the existing executor, not a process/command supplied by the request. Test callbacks are fakes or isolated temporary-config operations. The prototype itself does not install/run the helper or execute a managed-host operation.

## Required production dependencies and gates

1. An approved OIDC-backed human approval workflow with explicit approver role/scope authorization, separation-of-duties rules, immutable approval records and trusted issuer/key custody. The subject claim in a signed token alone is insufficient.
2. An authoritative Controller resolver for current target, enrolled agent identity, credential fingerprint, binding generation, assignment, policy/catalog state, assessment/evidence and exact plan or recovery manifest. Current provenance remains unresolved/untrusted for approval use.
3. Production agent enrollment and mTLS identity mapping with revocation/rotation. The current mTLS listener is read-only and local deployment is unverified.
4. A narrow OS helper/service and authenticated local IPC; OS ownership, socket permissions, path traversal/symlink/race resistance, process identity separation and only the fixed operation must be independently reviewed. No managed-host sudoers/systemd installation is approved by this ADR.
5. A protected durable replay/idempotency state machine and a durable audit sink/outbox with reconciliation for post-start audit outage. The Controller SQLite hash chain is not immutable and is not currently reachable as a trusted agent audit service.
6. Disposable Ubuntu VM tests with separate unprivileged agent and privileged helper accounts, isolated synthetic CA/approval keys, deterministic reset, no production trust roots/credentials, effective `sshd -T` validation, first-directive conflicts, concurrent/restarted replay, interrupted execution and recovery. VM integration is NOT run or passed by this ADR.
7. Independent security review and explicit release authorization before any production enablement. Keep `AGENT_EXECUTION_TOKEN` unset and no remote execution/rollback route available until the later policy-bound dispatch design is approved.

## Consequences

This batch can test strict parsing, cryptographic/binding rejection, atomic local replay reservation, pre-mutation audit denial, and isolated callback outcomes. It cannot assert production human authorization, deployment identity, trusted provenance, durable external audit, safe root delegation, or end-to-end execution. A valid test signature demonstrates verifier integration only; it is not evidence that a human approval authority exists.
